1.1. Бюджетирование проектов, финансовая аналитика и прогнозирование рисков

Для этой задачи лучше всего подойдёт реляционная СУБД, например PostgreSQL.

Финансовые данные требуют строгой структуры и высокой целостности. Необходимо хранить информацию о проектах, бюджетах, статьях расходов, платежах и плановых показателях. Между этими сущностями существуют связи, которые должны сохраняться корректно.

PostgreSQL поддерживает:

ACID-транзакции;
внешние ключи и ограничения целостности;
типизированные данные;
индексы;
сложные SQL-запросы;
представления и агрегатные функции.

Это позволяет выполнять финансовые операции согласованно и формировать отчёты по проектам, подразделениям и статьям расходов.

Для больших объёмов аналитики дополнительно можно использовать ClickHouse, куда будут передаваться данные из PostgreSQL. PostgreSQL при этом останется основной СУБД для оперативного хранения финансовой информации.

Вывод: PostgreSQL лучше всего подходит как основная СУБД для бюджетирования и финансового учёта благодаря строгой структуре, транзакционности и обеспечению целостности данных.

1.2. Лендинги девелоперских проектов и CRM

Для лендингов и CRM можно использовать документоориентированную СУБД, например MongoDB.

У разных девелоперских проектов лендинги могут иметь различные формы заявок и наборы полей. Например, на одном сайте пользователь оставляет заявку на покупку квартиры, на другом — записывается на консультацию, а на третьем — запрашивает коммерческое предложение.

MongoDB хранит данные в виде документов, структура которых может быть гибкой. Это позволяет добавлять новые поля и изменять структуру заявок без необходимости постоянно изменять схему таблиц.

Для CRM такая модель также удобна, поскольку можно хранить:

данные клиентов;
заявки с лендингов;
источники рекламы;
статусы лидов;
историю взаимодействий;
дополнительные параметры клиентов и сделок.

MongoDB хорошо подходит для быстрого приёма большого количества заявок и работы с гибкими структурами данных.

Вывод: для лендингов и CRM можно использовать MongoDB, поскольку она обеспечивает гибкость структуры документов и удобна для хранения быстро меняющихся данных.

1.3. База корпоративных норм, правил и обучающих материалов

Для этой задачи подойдёт реляционная СУБД, например PostgreSQL.

Корпоративные нормы, правила и обучающие материалы можно представить в виде простой и понятной структуры:

разделы;
подразделы;
документы;
версии документов;
авторы;
даты публикации;
статусы утверждения.

Реляционная модель позволяет организовать эти данные в связанные таблицы. Например, один раздел может содержать несколько документов, а каждый документ может иметь несколько версий.

PostgreSQL обеспечивает целостность связей между сущностями, поддерживает поиск, сортировку и фильтрацию документов. Кроме того, можно организовать разграничение доступа для сотрудников разных подразделений.

Для удобства пользователей поверх СУБД можно установить Wiki-систему или корпоративный портал. В таком случае PostgreSQL будет отвечать за хранение данных, а пользователи будут работать через понятный веб-интерфейс.

Вывод: PostgreSQL подходит для корпоративной базы знаний благодаря простой реляционной структуре, удобству поиска и возможности организовать права доступа.

1.4. Логистика: маршруты доставки материалов и распределение курьеров

Для этой задачи хорошо подойдёт графовая СУБД, например Neo4j.

Логистические данные содержат большое количество связей между объектами:

склады;
строительные объекты;
поставщики;
курьеры;
маршруты;
материалы;
пункты доставки.

В графовой модели объекты представляются узлами, а связи между ними — рёбрами. Например, склад связан с маршрутом, маршрут — с объектом строительства, а объект — с курьером.

Neo4j позволяет эффективно выполнять запросы, связанные со связями между объектами. Это может быть полезно для поиска маршрутов, анализа доступных путей, определения связанных объектов и распределения курьеров.

Для работы с географическими координатами и дорожной сетью также можно использовать PostgreSQL с расширением PostGIS. Такой вариант позволяет хранить координаты складов и объектов, выполнять географические запросы и интегрироваться с внешними сервисами маршрутизации.

### Задание 2. Транзакции
2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы транзакция завершилась успешно. Ориентируйтесь на шесть действий.

2.1.* Какие действия должны произойти, если пополнение счёта телефона происходило бы через автоплатёж?

Приведите ответ в свободной форме.

Рассмотрим транзакцию из шести последовательных действий:

Начало транзакции.
Система получает запрос пользователя на пополнение баланса и открывает транзакцию в базе данных.
Проверка данных.
Проверяются номер телефона, сумма пополнения, наличие необходимых средств на счёте пользователя и отсутствие других ограничений.
Списание средств со счёта пользователя.
Из баланса пользователя вычитается сумма пополнения. Операция выполняется внутри транзакции, поэтому изменения пока не считаются окончательно подтверждёнными.
Зачисление средств на баланс телефона.
На баланс указанного номера добавляется сумма пополнения.
Проверка результата операции.
Система проверяет, что списание и зачисление выполнены корректно, балансы соответствуют ожидаемым значениям, а ошибок не возникло.
Подтверждение транзакции (COMMIT).
Если все действия завершились успешно, система подтверждает транзакцию. Изменения сохраняются в базе данных, и пользователь получает сообщение об успешном пополнении.

Если на любом этапе произойдёт ошибка, выполняется ROLLBACK: списание и зачисление отменяются, а данные возвращаются к исходному состоянию. Это обеспечивает атомарность транзакции: операция выполняется либо полностью, либо не выполняется вообще.

### Задание 3. SQL vs NoSQL
3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL.

3.1.* Какие, на ваш взгляд, преимущества у NewSQL систем перед SQL и NoSQL.

Приведите ответ в свободной форме.

SQL-системы, или реляционные СУБД, имеют ряд преимуществ перед NoSQL-решениями. При этом важно учитывать, что конкретные характеристики зависят от выбранной СУБД и особенностей задачи.

1. Строгая структура данных.
В SQL-системах данные хранятся в таблицах с заранее определённой схемой. Это позволяет контролировать типы данных, обязательность полей и взаимосвязи между таблицами. Благодаря этому снижается вероятность появления некорректных или противоречивых данных.

2. Поддержка транзакций и целостности данных.
Реляционные СУБД поддерживают транзакции ACID, внешние ключи и ограничения целостности. Это особенно важно для финансовых операций, бухгалтерии, заказов и других задач, где данные должны изменяться согласованно.

3. Возможность выполнения сложных запросов.
SQL позволяет объединять данные из нескольких таблиц с помощью JOIN, выполнять группировку, сортировку, агрегатные вычисления и подзапросы. Это удобно для формирования отчётов и аналитики.

4. Зрелость и стандартизация.
SQL является широко распространённым языком, а реляционные СУБД существуют десятилетиями. Для них разработано большое количество инструментов, библиотек, средств резервного копирования, мониторинга и администрирования. Специалистов, знакомых с SQL, также достаточно много.

5. Удобство обеспечения согласованности связанных данных.
В SQL-системах можно явно описать связи между сущностями и гарантировать их корректность с помощью внешних ключей и ограничений. Например, нельзя создать заказ для несуществующего клиента или удалить запись, на которую ссылаются другие данные, если это нарушает заданные правила.

### Задание 4

Для такой задачи я бы выбирал тип СУБД прежде всего по характеру вычислений и способу обработки данных, а не просто по количеству машин. Важно понять, нужно ли выполнять сложные аналитические запросы по огромным объёмам данных, обрабатывать данные в реальном времени или выполнять множество независимых операций.

В данном случае, поскольку требуется производить большое количество вычислений над огромным количеством данных и выделено 1000 машин, наиболее подходящим вариантом будет распределённая аналитическая СУБД, например ClickHouse, либо связка Hadoop + Spark для более сложных задач обработки данных.

Критерии выбора СУБД

Я бы учитывал следующие критерии:

Объём данных.
Если данные не помещаются на одной машине, СУБД должна поддерживать горизонтальное масштабирование и распределённое хранение.
Тип нагрузки.
Для аналитических запросов по большим таблицам лучше подходят колоночные СУБД. Если требуется большое количество операций изменения отдельных записей, могут подойти другие решения.
Возможность параллельной обработки.
Система должна уметь распределять вычисления между несколькими машинами и объединять результаты.
Отказоустойчивость.
При выходе одной или нескольких машин из строя работа не должна полностью останавливаться. Для этого необходимы репликация и механизмы восстановления.
Стоимость и эффективность использования ресурсов.
Важно, чтобы добавление новых машин действительно увеличивало производительность, а не приводило к большим накладным расходам на обмен данными.
Какая модель распределённых вычислений подойдёт

Для такой задачи лучше всего подойдёт модель MapReduce, особенно если речь идёт о пакетной обработке огромных объёмов данных.

Работа MapReduce состоит из двух основных этапов:

Map — исходные данные разбиваются на части, и каждая машина независимо обрабатывает свою часть;
Reduce — результаты объединяются, группируются и агрегируются.

Например, если необходимо посчитать расходы по миллиардам строительных операций, данные можно разделить между 1000 машин. Каждая машина подсчитает расходы по своей части, а затем результаты будут объединены в общий итог.

Почему MapReduce подходит
позволяет обрабатывать данные параллельно на большом количестве машин;
хорошо масштабируется при увеличении объёма данных;
использует независимую обработку частей данных;
позволяет повторно выполнить отдельные задачи при сбоях;
подходит для пакетной аналитики и сложных вычислений.

При этом для современных задач я бы также рассмотрел Apache Spark, который реализует распределённую обработку данных и часто работает эффективнее классического MapReduce за счёт хранения промежуточных данных в памяти.
